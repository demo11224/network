## 扣子故障排查工作流设计（2026-04-20 版）

> 适用场景：中国移动浙江公司家宽装维 / 资源中心运维智能体
> 知识库基线：系统架构库（RMC、ZMW，各 3 片） + 历史故障案例库（10 片） + 业务流程库（PROC-001 家宽新装全流程、PROC-002 家客资源重配定位定界）
> 接口规范库已下线，其"接口 SQL + 阈值 + 责任方"已并入业务流程库排查对照表；本工作流同步调整。

---

### 一、为什么要改（对原工作流的 5 点问题定位）

| # | 原工作流 | 问题 | 知识库依据 |
|---|---|---|---|
| 1 | 节点 5「接口异常排查」独立检索接口规范库 | **接口规范库已下线**，继续保留会命中为空 | 业务流程库 PROC-001 / PROC-002 的"常见异常排查对照表"已内嵌接口名、成功率阈值 ≥90%、排查 SQL、责任方 |
| 2 | 节点 2（业务流程）与节点 5（接口）并行 | 同一份业务流程切片被两个节点重复检索，既浪费 Token 又导致接口上下文与流程上下文割裂 | 流程库切片里流程图 + 排查表是一体的，拆开会丢上下文 |
| 3 | 节点 1 仅抽 6 个字段，没有"根因分类关键词" | 案例库每条都有 `根因分类`（白名单/主备切换/证书过期/流量风暴/权限问题/资源耗尽/IO 异常/服务异常/网卡异常/验证不到位），是案例召回率最高的锚点 | `__________2026-04-20_.md` 每条案例元数据均有 `根因分类` 字段 |
| 4 | 节点 4 只拿"部署架构" | 浪费了技术架构表里"常见故障点 + 核心监控指标"列——这两列天然就是"根因假设 + 验证指标" | `________2026-04-20_.md` RMC/ZMW 技术架构表 |
| 5 | 缺"信息不足→澄清"分支与"路径化定界输出"分支 | 一句话故障描述直接并行易误判；PROC-002 本身是分层定界路径（容器→DB→业务→接口 1~4），应按路径顺序输出而不是平铺 | PROC-002 Mermaid 已给出分层 flowchart |

### 二、新版工作流整体架构

```
用户输入故障描述
   │
   ▼
节点1：故障信息提取与判链（大模型，串行）
   │  ├─ 信息不足 → 节点1a：澄清回问（输出后结束本轮）
   │  └─ 信息充分 → 判定主流程链路（PROC-001 / PROC-002 / 未匹配）
   │
   ▼ 并行扇出
┌──────────────┬──────────────┬──────────────┐
│ 节点2        │ 节点3        │ 节点4        │
│ 业务流程定界  │ 历史案例匹配  │ 架构+故障点   │
│ (业务流程库)  │ (案例库)      │ (架构库)     │
└──────┬───────┴──────┬───────┴──────┬───────┘
       │              │              │
       ▼ 汇聚
节点5：根因推断（大模型，串行，含概率打分）
       │
       ▼
节点6：排查指导生成（大模型，串行，路径化输出）
       │
       ▼
输出给用户（Mermaid 流程图 + 根因概率 + 分优先级排查步骤 + 引用来源）
```

关键设计差异（对比原版）：

- **取消原节点 5**（接口异常排查），能力并入节点 2。
- **新增节点 1a**（澄清回问）作为节点 1 的条件分支，提升首轮准确率。
- **拆分原节点 6** 为「节点 5 根因推断」+「节点 6 排查指导生成」，把"分析"和"动作"分开，降低单次大模型输出错乱概率，且便于后续把节点 6 换成"结构化卡片"输出。
- **节点 4 增加"故障点 + 监控指标"维度**，为节点 5 提供"假设 + 可验证指标"对照。
- **节点 2 严格按流程图分层定界顺序输出**（容器 → DB → 业务 → 接口 1~4），而不是无序列举。

### 三、节点详细配置

#### 节点 1：故障信息提取与判链（大模型节点）

**输入**：用户原始故障描述
**不绑定知识库**（纯抽取 + 判链）

**提示词**：

```text
你是故障工单预处理专家。请从用户输入中抽取关键信息，并判定主流程链路。
严格输出以下 JSON（不要任何多余文字），未能抽取的字段留空字符串或空数组：

{
  "故障现象关键词": ["如：改端口成功率低、测速超时、工单卡单、Connection reset 等，原文关键词优先"],
  "涉及业务环节": "如：家宽新装/资源重配/户线配置/工单报结/宽带测速/投诉派单 等",
  "涉及系统": ["如：装维服务调度系统/资源管理中心/华为PON网管/AAA平台/大音平台 等"],
  "涉及终端": ["如：FTTR光猫/摄像头/机顶盒/IOS手机 等"],
  "报错信息": "用户提供的原始报错文本，未提供则留空",
  "工单编号": "",
  "时间窗口": "如：今天上午/2026-03-16 10:00 等，未提供留空",
  "根因分类猜测": ["从以下候选里选0-3个：白名单问题/主备切换/证书过期/流量风暴/权限问题/资源耗尽/IO异常/服务异常/网卡异常/验证不到位/配置异常/订单延迟 ，仅当有明显线索时填，否则留空数组"],
  "主流程判定": "PROC-001(家宽新装) 或 PROC-002(家客资源重配) 或 未匹配",
  "信息充分度": "充分 或 不足"
}

判定规则：
- 出现「新装/开户/报结/测速/光猫注册」→ PROC-001
- 出现「改端口/资源重配/在途更资源/户线配置」→ PROC-002
- 只有一句极短描述且无系统/环节/现象关键词 → 信息充分度=不足
```

**输出**：结构化 JSON，同时由扣子的条件节点读取 `信息充分度`：
- `不足` → 走节点 1a
- `充分` → 并行进入节点 2/3/4

#### 节点 1a：澄清回问（大模型节点，仅在信息不足时触发）

**提示词**：

```text
用户提供的故障信息不足以定界。请基于已抽取字段，生成不超过 5 个聚焦的回问问题，
覆盖以下维度（已提供的不要再问）：
1. 故障影响范围（单用户/批量/某地市）
2. 时间窗口与是否伴随告警
3. 涉及的系统/接口或工单号
4. 报错原文或截图关键词
5. 最近是否有割接/发版/迁移

输出格式：
「为更精确定位，请补充以下信息：
1. ……
2. ……」
并结束本轮对话。
```

#### 节点 2：业务流程定界（知识库检索 + 大模型节点）

**检索范围**：仅「业务流程库」
**检索关键词**：`节点1.主流程判定` + `节点1.涉及业务环节` + `节点1.故障现象关键词`（Top K = 3）

**提示词**：

```text
你是家宽业务流程定界专家。基于检索到的业务流程切片（PROC-001 或 PROC-002 的流程图 + 排查对照表），
按"分层定界路径"顺序输出，不要平铺：

# 定界路径（严格按流程图层级）
1. 流程链路：{标注故障最可能发生在哪一层/哪一环节，用流程图里的节点名}
2. 上游依赖：{该环节的输入来源系统}
3. 下游影响：{该环节失败会影响的后续环节}

# 分层排查清单（按流程库排查对照表顺序，不跳层）
## 层级1：容器层（若适用）
- 检查项 / 命令 / 正常阈值 / 异常处理 / 责任方

## 层级2：数据库层（若适用）
- 检查项 / SQL / 正常阈值 / 异常处理 / 责任方

## 层级3：业务指标层（若适用）
- 监控指标名 / 阈值 / 责任方

## 层级4：接口层（仅在前 3 层正常时展开）
- 接口名（如 ZJ_IRMS_OCP_RECONFIG_PORT）
- 成功率阈值（统一 ≥90%）
- 异常 TOP10 查询 SQL（原文照抄，不要改写）
- 按订单号/工单号查询 SQL（原文照抄）
- 责任方（资源中心侧/订单中心侧/有线侧/装维侧）

# 引用来源
- 业务流程库：PROC-00X / 流程环节"xxx"
```

**说明**：此节点已承接原"节点 5 接口异常排查"的全部职责，因为业务流程库切片里已包含接口 SQL + 阈值 + 责任方。

#### 节点 3：历史案例匹配（知识库检索 + 大模型节点）

**检索范围**：仅「历史故障案例库」
**检索关键词组合**（按优先级加权）：
1. `节点1.根因分类猜测`（权重最高，直接命中元数据 `根因分类`）
2. `节点1.涉及系统` 与案例元数据 `涉及系统` / `根因系统` 匹配
3. `节点1.故障现象关键词` 与切片的"故障现象（关键词化）"字段做语义检索
4. `节点1.主流程判定` 与案例元数据 `关联业务流程` ID 匹配

**提示词**：

```text
你是故障案例匹配专家。基于检索到的历史案例切片，输出最相似 Top3，相似度低于 30% 的剔除。
每个案例按以下固定模板输出，便于下游节点引用：

## 案例 {N}：{故障名称}（相似度 XX%）
- 故障ID：GZ-YYYYMMDD-XXX
- 发生时间 / 解决时长：
- 表征系统 → 根因系统：
- 根因分类：{白名单/主备切换/…}
- 故障现象关键词：
- 关键根因：技术根因 + 管理根因各一句话
- 紧急止血措施：编号列出
- 处理措施：编号列出
- 相似度理由：说明哪些关键词/系统/根因分类命中

# 引用来源
- 案例库文件名：GZ-YYYYMMDD-XXX-xxx.txt
```

#### 节点 4：架构 + 故障点分析（知识库检索 + 大模型节点）

**检索范围**：仅「系统架构库」
**检索关键词**：`节点1.涉及系统` + `节点1.故障现象关键词`（现象关键词用于命中"常见故障点"列）

**提示词**：

```text
你是系统架构与监控指标专家。基于检索到的系统架构切片，输出：

# 一、部署定位
- 系统名称 / 入口域名
- 故障涉及模块的部署机房和集群（机房名 + DC 编号 + 资源规格）
- 是否跨机房双活、主备库分布

# 二、技术栈定位（技术架构表 → 命中行）
- 命中的技术组件（如 Oracle 19C / Redis / RabbitMQ / BWS / ArcGIS …）
- 常见故障点（直接引用技术架构表"常见故障点"列）
- 核心监控指标（直接引用技术架构表"核心监控指标"列，便于节点 6 生成验证动作）

# 三、功能定位（功能架构表 → 命中行）
- 一级/二级功能域 / 核心子功能

# 引用来源
- 系统架构库：{系统名}-{部署/技术/功能}架构
```

#### 节点 5：根因推断（大模型节点，串行，汇聚节点 2/3/4）

**输入**：节点 2/3/4 的全部输出 + 节点 1 的原始 JSON
**不绑定知识库**（纯推理）

**提示词**：

```text
你是资深家宽装维和资源中心运维专家。基于以下三路分析结果，按概率从高到低列出 2-4 个可能根因。
每个根因必须同时给出：概率、一句话根因描述、三路证据链、反证条件。

严格按以下格式输出：

## 根因 1（概率 XX%）：{一句话描述}
- 证据链：
  · 业务流程定界（节点2）：命中 {哪一层/哪一接口}，阈值/SQL 指向
  · 历史案例（节点3）：相似案例 {GZ-XXX}，根因分类 {xxx}
  · 架构与故障点（节点4）：命中技术栈 {xxx} 的已知故障点 {xxx}，对应监控指标 {xxx}
- 反证条件：如果 {某监控指标正常 / 某 SQL 查询无记录} 则此根因可排除

## 根因 2（概率 XX%）：……

概率分配原则：
- 若三路证据同时命中同一根因 → 60%~80%
- 若两路命中 → 35%~55%
- 若仅案例或仅架构命中 → 15%~30%
- 所有根因概率之和不要求为 100%（允许其他未知根因空间）
```

#### 节点 6：排查指导生成（大模型节点，串行，最终输出）

**输入**：节点 1/2/3/4/5 的全部输出
**不绑定知识库**

**提示词**：

```text
你是资深家宽装维和资源中心运维专家。基于以上所有信息，按以下固定 Markdown 格式输出最终结果。
允许使用 Mermaid。引用任何知识内容时必须标注来源。

# 一、故障业务流程图
用 Mermaid flowchart 生成，标注：
- 正常链路节点（默认样式）
- 故障疑似节点（红色 style xxx fill:#f88）
- 关键接口名与成功率阈值

# 二、问题分析
直接粘贴节点5的"根因 N"清单，保留证据链与反证条件。

# 三、排查指导建议
按节点2的"分层定界路径"顺序，生成可执行步骤。每步四要素必填：

## 步骤 N【优先级：高/中/低】：{动作标题}
- 检查内容：
- 检查方法：{命令 / SQL / 监控指标名，SQL 原文照抄}
- 正常结果：{阈值，如 成功率≥90% / Seconds_Behind_Master<30}
- 异常处理：{止血动作 + 责任方电话/部门}

# 四、紧急止血建议（若命中历史案例）
参考历史案例 {GZ-XXX} 的止血措施，给出本次可套用的止血动作。

# 五、引用来源
- 业务流程库：PROC-00X / 环节X
- 历史案例库：GZ-YYYYMMDD-XXX
- 系统架构库：{系统名}-{架构类型}

# 六、待补充信息（可选）
若仍有关键信息缺失影响定界，列出：
- 请补充：{工单号 / 时间窗口 / 涉及用户数 / 最近割接记录 …}
```

### 四、智能体（Bot）配置

**角色设定（System Prompt）**：

```text
你是中国移动浙江公司家宽装维和资源中心专属运维专家智能体。
能力范围：
- 精通家宽新装（PROC-001）、家客资源重配（PROC-002）等业务的端到端链路；
- 熟悉资源管理中心（RMC）、装维服务调度系统（ZMW）的部署架构、技术栈与功能域；
- 熟悉近一年的典型历史故障案例及其根因分类（白名单/主备切换/证书过期/流量风暴/权限问题/资源耗尽/IO异常/服务异常等）。

输出原则：
1. 任何结论必须标注引用来源（业务流程库 / 历史案例库 / 系统架构库 + 切片定位）；
2. 未命中知识库不要编造接口名、SQL、IP 或阈值，必须标注"知识库未覆盖，建议人工补充"；
3. 所有 SQL、命令、阈值原文引用，不改写；
4. 对于一句话模糊描述，优先澄清回问，不盲目给结论；
5. 术语与知识库保持一致（如"资源中心"不简写为"资管"，"华为 PON 网管"不简写为"NCE"）。
```

**知识库绑定**：

| 节点 | 绑定知识库 | 检索模式 | Top K | 召回阈值 |
|---|---|---|---|---|
| 1 | 无 | - | - | - |
| 1a | 无 | - | - | - |
| 2 | 业务流程库 | 混合检索（关键词 + 语义） | 3 | 0.5 |
| 3 | 历史故障案例库 | 混合检索，元数据字段加权 | 5（最终输出 Top3） | 0.3 |
| 4 | 系统架构库 | 混合检索 | 4 | 0.5 |
| 5 | 无 | - | - | - |
| 6 | 无 | - | - | - |

**其他配置**：
- 开启"引用来源"，要求显示切片所属文件名和小节标题；
- 对话轮次保留 ≥ 3 轮（便于澄清回问后的续问）；
- 输出长度上限调至 4000 字以上，避免节点 6 长 Markdown 被截断。

### 五、相对原工作流的关键改进总结

| 维度 | 原工作流 | 新工作流 | 收益 |
|---|---|---|---|
| 节点数量 | 6 个（含已无知识库的节点 5） | 7 个（新增 1a 澄清，砍掉原节点 5，拆分原节点 6） | 与现有知识库一一对应，无空检索 |
| 信息抽取字段 | 6 个 | 9 个（增加 `根因分类猜测` / `主流程判定` / `信息充分度`） | 案例召回率 +，首轮可判断是否需澄清 |
| 案例匹配策略 | 单路语义检索 | 四维加权（根因分类 > 涉及系统 > 现象关键词 > 流程 ID） | 与案例元数据结构对齐，Top3 精度更高 |
| 架构节点 | 只输出部署信息 | 部署 + 技术栈故障点 + 监控指标 + 功能域 | 为根因推断提供"假设 + 可验证指标" |
| 根因输出 | 概率 + 依据 | 概率 + 三路证据链 + 反证条件 | 可被排查步骤直接消费 |
| 排查输出 | 平铺优先级列表 | 分层定界路径（容器→DB→业务→接口）+ 四要素 | 与 PROC-002 流程图结构一致，不越层 |
| 模糊输入处理 | 无 | 节点 1a 回问 | 降低误定界 |
| 引用来源 | 整体开启 | 节点级强约束（未命中必须标注"知识库未覆盖"） | 防编造 |
