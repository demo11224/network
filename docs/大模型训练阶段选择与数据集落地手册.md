# 大模型训练阶段选择与数据集落地手册（傻瓜版）

> 回答三个问题：①我的任务该选哪个（哪几个）训练阶段？②每个阶段的数据集长什么样、怎么准备？③拿到数据后怎么真正跑起来？所有数据格式均来自 LLaMA-Factory 官方数据文档（`data/README_zh.md`），复制即可用。

---

## 第〇章 先建立一个正确的心智模型

**八个阶段不是八选一，而是一条流水线上的不同工位。** 一个模型的"出厂流程"分三大步：

```
第一步：预训练（PT/CPT）          第二步：SFT                第三步：偏好对齐
"读万卷书，学会说话"        "学会听指令、按要求干活"      "说得更好、更合人意"
      毛坯房          →           精装修           →          软装调优
                                                  ┌─ 路线A：RM → PPO（在线RL，大厂路线）
                                                  ├─ 路线B：DPO（主流默认）
                                                  ├─ 路线C：KTO（只有点赞/点踩时）
                                                  ├─ 路线D：ORPO（和SFT合并成一步）
                                                  └─ 路线E：SimPO（DPO的轻量替代）
```

三个新手必须先知道的事实：

1. **你 99% 不需要做预训练。** 从零预训练是千万美元级的事。你的起点永远是 Qwen、Llama 这类开源基座——它们已经替你完成了第一步。你需要考虑的只有"继续预训练（CPT）"，且仅当你有 GB 级领域语料时。
2. **RM、PPO、DPO、KTO、ORPO、SimPO 全是"第三步对齐"的六种不同实现，互相是替代关系，不是叠加关系。** 你只会从中选一条路线，不存在"DPO 完了再 KTO 再 SimPO"的标准流程。
3. **80% 的业务做完 SFT 就该停下来看效果。** 对齐阶段解决的是"回答对了但不够好"（啰嗦、语气不对、不安全、不合偏好），如果 SFT 后效果已达标，后面全不用做。

## 第一章 我的任务该选哪条流水线？

### 1.1 对号入座表（先查这张表）

| 你的情况（说人话版） | 选择的流水线 | 出处/先例 |
|---|---|---|
| 想让模型干一件具体的活：分类、信息抽取、按格式输出 JSON、客服问答、风格化写作 | **只做 SFT**，做完就停 | 绝大多数业务的终点 |
| SFT 后"答得对但不好"：太啰嗦 / 语气不对 / 偶尔说不该说的 / 两个回答里总挑差的那个 | **SFT → DPO**（默认对齐路线） | Zephyr、Tülu 2 的标准做法 |
| 没有"A比B好"的成对数据，只有线上点赞/点踩、工单解决/未解决这类**单条好坏标记** | **SFT → KTO** | KTO 论文（Ethayarajh 2024） |
| 想省事：不想跑两阶段，希望一次训练同时完成 SFT 和对齐 | **ORPO 单步**（用偏好数据直接训基座） | ORPO 论文（Hong 2024） |
| 已经有一个不错的 Instruct 模型，想再拔高一档，且显存紧张 | **SimPO**（无参考模型，省显存） | SimPO 论文（Meng 2024） |
| 有人力做大量人工标注、有 GPU 集群、追求效果天花板（如做通用助手产品） | **SFT → RM → PPO** | InstructGPT、Llama 2 |
| 模型缺领域知识：说不出专业术语、领域问题胡编（医疗/法律/金融等） | **CPT → SFT（→ DPO）**；没有 GB 级语料就别训，上 RAG | Biderman 2024 的结论 |
| 想训练模型学会调用工具/Function Call | **SFT**（用带 function_call 的 sharegpt 数据） | — |
| 多模态（看图说话、图文问答） | **SFT**（带 images 列的多模态数据） | LLaVA 范式 |

### 1.2 五个问题的决策问答（按顺序自问）

```
问1：现成模型 + 好的提示词 + RAG，能解决吗？
     → 能：不要训练。结束。
     → 不能，继续↓

问2：模型是"不会干这个活"，还是"缺知识"？
     → 不会干活（格式不对、不听指令、风格不符）→ SFT，去问3
     → 缺知识（术语都不认识、内容胡编）→ 有 GB 级领域文本就 CPT→SFT；
       没有就 RAG + SFT（把知识放进 prompt，SFT 只教它怎么回答）

问3：SFT 训完，盲测效果达标了吗？
     → 达标：上线。结束（80% 的项目到此为止）。
     → 输出"对但不好"，继续↓

问4：你手里的反馈数据长什么样？
     → 能拿到/能造出"同一问题的好回答+坏回答"成对数据 → DPO（默认）
     → 只有单条回答的好/坏标记（点赞点踩）→ KTO
     → 什么反馈都没有但想省两阶段 → 回去造偏好数据，用 ORPO 一步训

问5：你有训练 RM 的标注预算 + 跑 PPO 的集群和调参人力吗？
     → 没有（绝大多数团队）→ 维持问4的选择
     → 有，且 DPO 已到瓶颈 → SFT → RM → PPO
```

### 1.3 容易混淆的三个问题

- **"要不要单独训奖励模型（RM）？"** 只有 PPO（以及拒绝采样、Best-of-N 这类用法）需要 RM。**DPO/KTO/ORPO/SimPO 都不需要训 RM**——这正是它们流行的原因。
- **"ORPO 和 SFT→DPO 怎么选？"** ORPO 把两步并成一步，省算力省流程，但它同时承担 SFT 的职责，**偏好数据量要按 SFT 量级准备**（数万对），只有几千对时老老实实 SFT→DPO。
- **"SimPO 和 DPO 怎么选？"** SimPO 不需要参考模型，显存更省、超参更敏感；它必须从已经 SFT 过的模型出发。稳妥默认 DPO，显存紧张或想冲分再试 SimPO。

## 第二章 每个阶段的数据集长什么样（复制即用）

通用规则：数据文件是 json/jsonl，放进 LLaMA-Factory 的 `data/` 目录，并在 `data/dataset_info.json` 里注册一条描述，训练配置里写 `dataset: 你的数据集名` 即可。

### 2.1 继续预训练（CPT）数据：纯文本

训什么：让模型"读"领域文档，学知识。**不是问答对，就是原始文本。**

```json
[
  {"text": "保险合同中的犹豫期是指投保人收到保险合同并书面签收之日起的一段时期，通常为15-20天。在此期间，投保人可以无条件解除合同，保险公司应退还已收取的全部保费……"},
  {"text": "《中华人民共和国保险法》第十六条规定，订立保险合同，保险人就保险标的或者被保险人的有关情况提出询问的，投保人应当如实告知……"}
]
```

`dataset_info.json` 注册：

```json
"my_domain_corpus": {
  "file_name": "my_domain_corpus.json",
  "columns": { "prompt": "text" }
}
```

| 要点 | 说明 |
|---|---|
| 数据量 | **至少 1 亿（100M）token**，低于这个量基本无感，别浪费卡时 |
| 怎么造 | 领域书籍/法规/内部文档/爬取语料 → 清洗（去页眉页脚、去乱码、去重）→ 切成自然段落 |
| 最大的坑 | 拿几万条 QA 对当 CPT 语料——量级差了三个数量级，学不到知识 |

### 2.2 SFT 数据：指令 + 标准答案（alpaca 格式）

训什么：教模型"接到什么指令，给出什么回答"。**这是最重要的数据，质量决定一切。**

```json
[
  {
    "instruction": "客户咨询：我的快递三天了还没到，怎么回事？",
    "input": "",
    "output": "非常抱歉给您带来不便！请您提供一下订单号，我马上为您查询物流状态。一般情况下，同城快递1-2天送达，跨省3-5天。如果超出时效，我们会立即联系承运方为您加急处理，并视情况为您申请运费补偿。",
    "system": "你是XX商城的金牌客服，回答要热情、简洁、给出可执行的解决步骤。"
  },
  {
    "instruction": "把下面的用户评价分类为：好评/中评/差评，只输出类别。",
    "input": "东西还行吧，就是物流太慢了，等了一个星期。",
    "output": "中评"
  },
  {
    "instruction": "客户说优惠券用不了",
    "input": "",
    "output": "请您先检查三点：1）优惠券是否在有效期内；2）订单金额是否达到使用门槛；3）该商品是否在优惠券适用范围内。如果都符合仍无法使用，请截图发给我，我帮您人工处理。",
    "history": [
      ["你们家优惠券怎么领？", "您可以在App首页点击'领券中心'，每天上午10点更新，会员还有专属券哦。"]
    ]
  }
]
```

`dataset_info.json` 注册：

```json
"my_sft_data": {
  "file_name": "my_sft_data.json",
  "columns": { "prompt": "instruction", "query": "input", "response": "output", "system": "system", "history": "history" }
}
```

（多轮对话/工具调用/多模态用 sharegpt 格式，`conversations` 列里放 `{"from": "human/gpt", "value": "..."}` 的消息列表，注册时加 `"formatting": "sharegpt"`。）

| 要点 | 说明 |
|---|---|
| 数据量 | 风格/格式任务 500~5k 条；领域问答 5k~5 万条；通用助手 5 万条以上 |
| 怎么造（三个来源，按优先级） | ① **线上真实日志**：挑出人工客服回答得好的对话，洗成问答对（最值钱）；② **强模型生成+人工审**：用 GPT-4o/DeepSeek 级模型按你的业务规则批量生成，再人工抽检修改；③ **人工编写**：覆盖高频问题 + 边角案例 |
| 最大的坑 | `output` 必须是"**你希望模型说出的完美答案**"，不是现状记录。把真实客服的敷衍回答直接当训练数据，模型就学会敷衍 |
| 第二大坑 | 不掺通用数据。领域:通用 ≈ 1:1~1:5 混入开源通用指令集（如 alpaca_zh），防止模型变成只会一件事的呆子 |

### 2.3 偏好数据：好回答 + 坏回答（RM / DPO / ORPO / SimPO 四个阶段通用同一格式）

训什么：教模型"同一个问题，这样答好，那样答不好"。**一份数据，四种训法都能喂**，这是性价比最高的标注投资。

```json
[
  {
    "instruction": "客户投诉：你们的售后太差了，打电话没人接！",
    "input": "",
    "chosen": "非常抱歉让您有这样糟糕的体验！您的心情我完全理解。请您把联系方式和问题留给我，我现在就为您建立加急工单，2小时内必定有专人回电。同时我先在线帮您处理，请问您遇到的具体问题是什么？",
    "rejected": "售后电话忙线是正常的，建议您换个时间再打，或者在App上自助提交工单。"
  },
  {
    "instruction": "用一句话总结这段话的核心观点。",
    "input": "近年来，随着新能源汽车渗透率快速提升，充电基础设施建设滞后的问题日益突出，节假日高速服务区排队充电已成常态……",
    "chosen": "新能源汽车增长太快，充电桩建设没跟上，节假日充电难成了普遍问题。",
    "rejected": "这段话主要讲了以下几点：第一，新能源汽车渗透率在提升；第二，充电基础设施建设滞后；第三，节假日高速服务区出现排队充电现象；综上所述，核心观点是充电设施与车辆增长不匹配。"
  }
]
```

`dataset_info.json` 注册（注意 `ranking: true`）：

```json
"my_pref_data": {
  "file_name": "my_pref_data.json",
  "ranking": true,
  "columns": { "prompt": "instruction", "query": "input", "chosen": "chosen", "rejected": "rejected" }
}
```

| 要点 | 说明 |
|---|---|
| 数据量 | DPO/SimPO：2k~5 万对；ORPO（兼任SFT）：数万对起；RM：5k~10 万对 |
| 怎么造（三种方法） | ① **人工二选一**：把模型的两个回答给标注员挑（质量最高）；② **强模型当裁判**：让自己的模型生成回答当 rejected，GPT-4o 级模型的回答或改写版当 chosen；③ **自采样+打分**（最推荐，SimPO 论文做法）：用你 SFT 后的模型对同一问题生成 5 个回答，用规则或评分模型选最好的当 chosen、最差的当 rejected——这是"on-policy"数据，效果最好 |
| 最大的坑 | rejected 不能是乱码或胡话——它应该是"**看起来还行但确实差一点**"的回答（啰嗦、语气生硬、漏要点）。差距太悬殊模型学不到有用的边界 |
| 第二大坑 | 长度偏置：如果所有 chosen 都比 rejected 长，模型学到的是"越长越好"，越训越啰嗦。刻意混入"chosen 更短"的样本 |

### 2.4 KTO 数据：单条回答 + 好/坏标记（sharegpt 格式 + kto_tag）

训什么：和偏好数据目的一样，但**不需要成对**，每条数据只有一个回答和一个 true/false 标记。完美对接线上点赞/点踩日志。

```json
[
  {
    "conversations": [
      { "from": "human", "value": "我的订单怎么还没发货？" },
      { "from": "gpt", "value": "您好！请提供订单号，我立即为您查询。目前大促期间发货时效为48小时内，如已超时我会为您催促仓库优先处理。" }
    ],
    "kto_tag": true
  },
  {
    "conversations": [
      { "from": "human", "value": "我的订单怎么还没发货？" },
      { "from": "gpt", "value": "发货时间以页面显示为准。" }
    ],
    "kto_tag": false
  }
]
```

`dataset_info.json` 注册：

```json
"my_kto_data": {
  "file_name": "my_kto_data.json",
  "formatting": "sharegpt",
  "columns": { "messages": "conversations", "kto_tag": "kto_tag" }
}
```

| 要点 | 说明 |
|---|---|
| 数据量 | 1 万条起步；好/坏比例 1:1 最稳，论文证明不平衡也能训（KTO 的卖点之一） |
| 怎么造 | 直接导线上日志：点赞=true，点踩=false；客服场景可用"工单是否一次解决""用户是否追问同一问题"做隐式标记 |
| 最大的坑 | 点踩的原因五花八门（答错了/态度差/没听懂），如果坏样本里混着大量"事实错误"，KTO 会教模型回避而不是改进——先按点踩原因过滤一遍 |

### 2.5 PPO 数据：只需要问题（prompt），不需要答案

训什么：PPO 是让模型自己生成回答、由 RM 打分、按分数更新。所以**数据集里只要 prompt**（复用 SFT 格式，只有 `instruction` 列会被使用），外加一个**已经训好的 RM**。

```json
[
  { "instruction": "客户咨询：退货运费谁出？", "input": "", "output": "" },
  { "instruction": "帮我写一封催供应商发货的邮件，语气要客气但坚决。", "input": "", "output": "" }
]
```

| 要点 | 说明 |
|---|---|
| 数据量 | 1 万~10 万条多样化 prompt，覆盖你的真实使用分布 |
| 前置条件 | 必须先完成：SFT 模型 + RM（用 2.3 的偏好数据训练，`stage: rm`） |
| 最大的坑 | prompt 分布太窄 → 模型只在窄分布上讨好 RM，泛化崩坏（reward hacking）。prompt 多样性比数量更重要 |

### 2.6 一张总表：阶段 ↔ 数据格式对应关系

| 训练阶段 | 数据格式 | 核心字段 | dataset_info 关键项 | 最低起步量 |
|---|---|---|---|---|
| CPT | 纯文本 | `text` | `columns.prompt: text` | 100M token |
| SFT | 指令问答 | `instruction / input / output` | 默认即可 | 500 条（窄任务） |
| RM | 偏好对 | `instruction / chosen / rejected` | `ranking: true` | 5k 对 |
| PPO | 仅 prompt | `instruction` | 默认即可 | 1 万条 prompt + 已训 RM |
| DPO | 偏好对 | 同 RM | `ranking: true` | 2k~5k 对 |
| KTO | 单条+标记 | `conversations / kto_tag` | `formatting: sharegpt` + `kto_tag` | 1 万条 |
| ORPO | 偏好对 | 同 RM | `ranking: true` | 数万对（兼任 SFT） |
| SimPO | 偏好对 | 同 RM | `ranking: true` | 2k~5k 对（建议自采样造数据） |

**记忆口诀：CPT 喂文章，SFT 喂问答，对齐喂好坏——成对的走 DPO/ORPO/SimPO/RM，不成对的走 KTO，啥都不喂只给问题的是 PPO。**

## 第三章 实际开训（LLaMA-Factory 全流程命令）

### 3.1 装环境（一次性）

```bash
git clone --depth 1 https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory
pip install -e ".[torch,metrics]"
# 显存不够要用 QLoRA 的再装：pip install bitsandbytes
```

把你的数据文件放进 `data/`，并在 `data/dataset_info.json` 中按第二章的方式注册。

### 3.2 第一步：SFT（LoRA，单张 24G 卡即可跑 7B）

新建 `sft_lora.yaml`：

```yaml
### 模型
model_name_or_path: Qwen/Qwen2.5-7B-Instruct

### 方法
stage: sft
do_train: true
finetuning_type: lora
lora_rank: 16
lora_alpha: 32
lora_target: all          # 关键：挂所有线性层，不要只挂 q,v

### 数据（领域数据 + 通用数据混合防遗忘）
dataset: my_sft_data,alpaca_zh_demo
template: qwen
cutoff_len: 2048
max_samples: 100000

### 训练
output_dir: saves/qwen2.5-7b/lora/sft
per_device_train_batch_size: 2
gradient_accumulation_steps: 8
learning_rate: 1.0e-4     # LoRA 学习率，比全参高一个数量级
num_train_epochs: 3.0
lr_scheduler_type: cosine
warmup_ratio: 0.1
bf16: true
logging_steps: 10
save_steps: 200

### 验证（一定要留验证集盯过拟合）
val_size: 0.05
per_device_eval_batch_size: 2
eval_strategy: steps
eval_steps: 200
```

开训、试聊、合并导出：

```bash
llamafactory-cli train sft_lora.yaml
llamafactory-cli chat --model_name_or_path Qwen/Qwen2.5-7B-Instruct \
    --adapter_name_or_path saves/qwen2.5-7b/lora/sft --template qwen
llamafactory-cli export --model_name_or_path Qwen/Qwen2.5-7B-Instruct \
    --adapter_name_or_path saves/qwen2.5-7b/lora/sft \
    --template qwen --export_dir models/qwen2.5-7b-sft
```

> 显存不够（如只有 12G）：加两行 `quantization_bit: 4` 和 `quantization_method: bnb` 即变 QLoRA，其他不用动。

### 3.3 第二步（可选）：DPO（从 SFT 产物继续）

新建 `dpo_lora.yaml`，关键差异四处——`stage: dpo`、数据换成偏好集、**学习率降两个量级**、基座换成合并后的 SFT 模型：

```yaml
model_name_or_path: models/qwen2.5-7b-sft   # 第一步导出的模型
stage: dpo
do_train: true
finetuning_type: lora
lora_rank: 16
lora_alpha: 32
lora_target: all
pref_beta: 0.1
pref_loss: sigmoid        # 标准 DPO；改成 orpo 或 simpo 即切换算法

dataset: my_pref_data     # ranking: true 的偏好数据
template: qwen
cutoff_len: 2048

output_dir: saves/qwen2.5-7b/lora/dpo
per_device_train_batch_size: 1
gradient_accumulation_steps: 8
learning_rate: 5.0e-6     # 偏好训练学习率必须比 SFT 低很多，照搬 SFT 学习率必训崩
num_train_epochs: 1.0
lr_scheduler_type: cosine
warmup_ratio: 0.1
bf16: true
```

```bash
llamafactory-cli train dpo_lora.yaml
```

### 3.4 其他路线只改两个参数

| 想跑的算法 | 改法 | 用的数据 |
|---|---|---|
| KTO | `stage: kto`，删掉 pref_loss | 2.4 的 kto_tag 数据 |
| ORPO | `stage: dpo` + `pref_loss: orpo`，**model_name_or_path 直接用基座**（不需要先 SFT） | 2.3 偏好数据（量要大） |
| SimPO | `stage: dpo` + `pref_loss: simpo`（基座必须是 SFT/Instruct 模型） | 2.3 偏好数据 |
| RM | `stage: rm` | 2.3 偏好数据 |
| PPO | `stage: ppo` + `reward_model: <RM输出目录>` | 2.5 的 prompt 数据 |
| CPT | `stage: pt` | 2.1 的纯文本数据 |

### 3.5 关键超参速查（背下来能避开 80% 的训崩）

| 阶段 | LoRA 学习率 | 全参学习率 | epoch | 特有关键参数 |
|---|---|---|---|---|
| CPT | 5e-5~1e-4 | 1e-5~5e-5 | 1 | — |
| SFT | 1e-4~3e-4 | 1e-5~2e-5 | 2~3（小数据）/ 1~2（大数据） | cutoff_len 按数据实际长度定 |
| RM | 1e-4 | 1e-5 | 1 | — |
| DPO/SimPO | 5e-6~5e-5 | 5e-7~1e-6 | 1 | pref_beta 0.1（SimPO 用 2.0~2.5 + gamma） |
| KTO | 5e-6~5e-5 | 5e-7~1e-6 | 1 | 好坏样本权重可调 |
| ORPO | 1e-4（兼任SFT，可稍高） | 8e-6 | 1~3 | orpo 系数默认 0.1 |

## 第四章 三个端到端配方（照抄就能跑通流程）

### 配方一：智能客服（最常见）

1. 从工单系统导出 3 个月人工客服优秀对话 → 清洗成 SFT 数据 5000 条（2.2 格式，含 history 多轮）；
2. 混入 5000 条开源通用中文指令数据；
3. 按 3.2 跑 SFT LoRA，盲测 50 个真实问题，达标就上线；
4. 上线后收集点赞/点踩 3 周 → 攒 1 万条 KTO 数据（2.4 格式）→ `stage: kto` 再训一轮；
5. 循环第 4 步。**全程不需要 RM、PPO。**

### 配方二：法律领域问答

1. 先做 RAG 基线（法条放检索库），评估：如果 RAG + 通用模型已达标，**到此为止**；
2. 不达标且手里有 5GB 以上法律文书/法条/案例 → CPT（2.1 格式，`stage: pt`，全参或 Freeze，参考主指南第六章——这一步 LoRA 不胜任）；
3. CPT 产物上做 SFT：1~2 万条"法律问题→专业回答"（强模型起草+律师审校）；
4. 用 SFT 模型自采样造 5000 偏好对（2.3 的方法③）→ DPO。

### 配方三：公文/文案风格写作助手

1. 收集 800 篇范文，为每篇逆向构造指令（"写一份关于XX的通知"→范文原文）；
2. SFT LoRA，r=8 即可，3 epoch；
3. 结束。**风格类任务是 LoRA 最强场景，不需要任何对齐阶段。**

## 第五章 新手最容易死的 10 个坑

1. **跳过"要不要训"的判断**——先试提示词和 RAG，训练是最后手段。
2. **拿 QA 对做知识注入**——几万条 QA 学不会知识，知识要 CPT（100M token 起）或 RAG。
3. **SFT 数据里混入烂答案**——模型是复读机，喂什么学什么，`output` 必须是完美答案。
4. **不混通用数据**——纯领域数据训完，模型连"你好"都答不利索。
5. **偏好训练照搬 SFT 学习率**——DPO 系学习率要再低 1~2 个数量级，否则必崩。
6. **rejected 造得太烂**——拿乱码当坏例子，模型学不到有用边界。
7. **chosen 全比 rejected 长**——训出越来越啰嗦的模型。
8. **不留验证集**——`val_size: 0.05` 写上，eval loss 开始涨就是过拟合信号，立即停。
9. **训完不做盲测就上线**——固定 50~100 个真实问题，每轮训练后人工盲评对比，这是唯一可信的验收方式，benchmark 分数不能代替。
10. **一次改多个变量**——数据、超参、方法一起换，效果变了不知道归因给谁。每轮只改一件事。

## 第六章 基座模型怎么选（训练之前最重要的决定）

### 6.1 Base 版还是 Instruct/Chat 版？

这是新手最常选错的一步：

| 你的流水线 | 选哪个 | 原因 |
|---|---|---|
| 只做 SFT（轻量业务微调，几千~几万条） | **Instruct 版**（如 Qwen2.5-7B-Instruct） | 它已具备指令遵循和安全对齐，你只需在上面叠加业务能力，少量数据就够 |
| 完整流水线：大规模 SFT → 偏好对齐 | **Base 版**（如 Qwen2.5-7B） | 你要自己控制全部对齐过程；在 Instruct 上做大规模 SFT 会和官方对齐"打架"，行为难预测 |
| CPT 领域注入 | **Base 版** | CPT 会冲掉对话能力，反正后面要重做 SFT，从 Base 开始更干净 |
| ORPO 一步训练 | Base 版（论文设置）或 Instruct 均可 | ORPO 自带 SFT 职责 |
| SimPO | **必须 Instruct/SFT 后的模型** | 论文明确从 SFT 模型出发 |

### 6.2 模型大小：用部署条件倒推，不要用效果正推

正确顺序是先问"我上线时给多少推理预算"，再决定训多大的模型：

| 推理条件 | 该选的规模 | 备注 |
|---|---|---|
| CPU / 端侧 / 极低成本 | 0.5B~3B | 任务必须足够窄（分类、抽取），配合全参微调 |
| 单张消费卡（4090）在线服务 | 7B~14B（量化后） | 业务微调的主流甜点位 |
| 单张 A100/H100 或可接受多卡 | 32B~72B | 复杂推理、高要求生成 |
| 调 API 不自部署 | 不用训自己的模型，先确认 API + 提示词真的不行 | — |

经验：**任务窄、判断标准明确 → 小模型 + 微调常常打平大模型 + 提示词，且推理成本低一个数量级**；任务开放、需要常识推理 → 模型大小是硬天花板，小模型怎么训都到不了。

### 6.3 其他必查项（5 分钟避免返工）

- **许可证**：Qwen（Apache 2.0 系）、Llama（自有许可，有月活限制条款）、商用前读一遍 LICENSE；
- **中文能力**：中文业务优先选中文语料占比高的模型家族（Qwen、GLM、DeepSeek），不要拿英文模型硬训中文；
- **上下文长度**：你的 prompt + RAG 检索内容 + 回答加起来多长？超过基座原生长度就要考虑长上下文版本；
- **生态**：选社区量化版本齐全（GPTQ/AWQ/GGUF）、vLLM 支持好的主流家族，部署时少踩一半的坑。

## 第七章 效果评估与验收（不做这章，前面全白训）

### 7.1 训练前先建"盲测集"——这是整个项目最值钱的资产

1. 收集 **50~200 个真实问题**（从工单、日志、业务方那里要），覆盖：高频问题（60%）+ 边角案例（25%）+ 不该回答/超范围的问题（15%）；
2. **永远不放进训练集**，锁起来；
3. 每个问题写清楚"好答案的标准"（要点列表，而不是标准答案全文）。

### 7.2 三层评估，缺一不可

| 层 | 做法 | 频率 | 看什么 |
|---|---|---|---|
| ① 训练指标 | eval loss（`val_size: 0.05`） | 每次训练自动 | 只能看出"有没有训崩/过拟合"，**看不出业务效果** |
| ② 盲测对比 | 新旧模型对盲测集各答一遍，打乱顺序人工评（A好/B好/平手） | 每个候选版本 | 上线与否的**唯一依据**。新模型胜率 > 55% 再考虑上线 |
| ③ 通用能力回归 | 跑 CEval/MMLU 抽样 + 20 条日常闲聊 | 每个候选版本 | 防灾难性遗忘：领域能力涨了，通用能力掉超过 3 个点就要回查数据配比 |

### 7.3 用大模型当裁判（LLM-as-Judge）的正确姿势

人工盲测贵，可以用 GPT-4o 级模型批量预筛，但要防三个已知偏置：

- **位置偏置**：裁判偏爱先出现的回答 → 每对回答正反序各评一次，结果不一致算平手；
- **长度偏置**：裁判偏爱长回答 → 评分 prompt 里明确写"简洁完整优于冗长"；
- **自恋偏置**：裁判偏爱和自己风格像的回答 → 关键版本仍要人工抽检 20%~30% 对照校准。

结论：LLM 裁判用于**版本间快速筛选**，上线决策仍以人工盲测为准。

### 7.4 上线后：A/B 与业务指标闭环

- 灰度 5%~10% 流量跑新模型，对比**业务指标**（解决率、转人工率、点踩率、用户追问率），不是模型指标；
- 至少跑一周再放量（周末/工作日分布不同）；
- 留好一键回滚：上一版模型常驻待命。

## 第八章 训练过程监控与故障排查

### 8.1 loss 曲线怎么看（SFT 为例）

- 正常形态：初始 1.5~3（在 Instruct 模型上继续训会更低），前 10% 步数快速下降，之后缓慢下降到 0.5~1.5 区间趋平；
- **train loss 降、eval loss 开始回升** = 过拟合，取 eval loss 最低的 checkpoint，别用最后一个；
- loss 低到 0.1 以下：大概率数据高度模板化/重复，模型在背书，盲测必翻车；
- DPO 看的不是 loss 绝对值，看 `rewards/accuracies`（chosen 得分高于 rejected 的比例），稳定爬到 0.7+ 算正常。

### 8.2 故障排查表（按出现频率排序）

| 症状 | 最可能原因 | 处理 |
|---|---|---|
| CUDA OOM | batch/序列太长 | 按顺序试：确认 gradient checkpointing 开了 → batch 降为 1 + 梯度累积 → 缩 cutoff_len → 换 QLoRA → 加卡 |
| loss 不降（平线） | LoRA 学习率给成了全参量级（1e-5） | LoRA 升到 1e-4 量级；确认 `lora_target: all` |
| loss = NaN / 突然爆炸 | 学习率太大、坏样本（超长/乱码）、fp16 溢出 | 降学习率一半；用 bf16 别用 fp16；检查数据里的异常长样本 |
| 训完复读机（同一句话循环） | 数据太单一/过拟合、epoch 太多 | 减 epoch、加数据多样性、推理时检查 repetition_penalty |
| 训完不听指令了/答非所问 | template 配错（模型与模板不匹配） | 训练和推理的 `template` 必须与基座一致（qwen 配 qwen），这是最隐蔽的高频错误 |
| 领域变强、闲聊变傻 | 灾难性遗忘 | 掺通用数据重训；或与原模型做权重插值融合 |
| DPO 后模型变啰嗦 | 偏好数据长度偏置 | 检查 chosen/rejected 长度分布，补"短即好"样本 |
| 训练极慢 | 没开 packing/FlashAttention，padding 浪费 | `packing: true`（CPT/短数据 SFT 收益最大）、`flash_attn: fa2` |

### 8.3 必须留档的训练记录

每次实验记录：数据版本及条数、基座、全部超参（yaml 直接入 git）、loss 曲线截图、盲测结果。**只改一个变量**的纪律靠记录执行——没有记录就没有归因，没有归因就是抽奖。

## 第九章 部署上线与迭代运营

### 9.1 从训练产物到线上服务

```
LoRA adapter ──merge──→ 完整模型 ──量化(GPTQ/AWQ)──→ vLLM/SGLang 部署
```

- **merge 再部署**是默认路线：零推理开销，和部署原版模型完全一样；
- **量化选型**：训练时的 QLoRA(bnb 4bit) 是"训练用量化"，**部署请用推理专用量化 GPTQ/AWQ/FP8**（吞吐高得多）；7B 量化后单卡 4090 可服务；
- **QLoRA 的 merge 坑**：adapter 要合并到 **bf16 原版基座**上再做部署量化，不要直接在 4-bit 模型上合并；
- **多业务共享基座**：vLLM 支持 multi-LoRA serving（一个基座同时挂 N 个 adapter，按请求路由），多租户场景一张卡服务多个业务，此时**不要 merge**。

### 9.2 上线检查清单

- [ ] 推理参数定版：temperature/top_p/repetition_penalty/max_tokens 用盲测时的同一套，**别用框架默认值**
- [ ] template 与训练时一致（再查一遍，上线事故高发点）
- [ ] 压测：目标 QPS 下的 P99 延迟、显存峰值
- [ ] 兜底：超时/超范围问题转人工或转规则回复
- [ ] 日志：保存输入输出（脱敏后），这是下一轮训练数据的来源

### 9.3 数据飞轮：让模型每个月自己变好

```
上线 → 收集日志（点赞/点踩、转人工、用户改写追问）
    → 每周人工审一批坏案例，修成 SFT 数据；点赞点踩攒成 KTO 数据
    → 每 2~4 周增量重训一版（在最新数据全集上重训，而非在旧 adapter 上续训）
    → 盲测对比 → 胜出则灰度发布
```

三条运营纪律：

1. **重训永远用"全量数据从基座重训"，不要在上一版 adapter 上继续训**——后者会累积漂移且无法归因；
2. 数据集和模型一样要有版本号（`sft_v3_20260610`），数据回滚比模型回滚更常用；
3. 坏案例修复后**加进盲测集**，防止同一问题在未来版本复发（回归测试思维）。

### 9.4 什么时候需要重训（而不是改提示词）

| 情况 | 动作 |
|---|---|
| 个别问题答错 | 先试提示词/RAG 修补，攒满一批再随下轮重训 |
| 新业务品类上线 | 补该品类 SFT 数据重训 |
| 点踩率持续爬升 | 拉坏案例分析：知识过时→更新 RAG；行为问题→重训 |
| 换基座（新一代模型发布） | 全量数据在新基座上重训一遍，通常白赚一截效果——**这是积累数据资产的意义：数据不依赖模型，模型会过时，数据不会** |

## 第十章 安全与合规（出事就是大事的部分）

1. **微调会削弱安全对齐**——这是有大量研究证实的现象：即使训练数据完全无害，SFT 也会让 Instruct 模型的拒答能力退化。对策：训练数据里掺 5%~10% 安全样本（有害问题 → 得体拒答），上线前用一批红线问题（违法、自伤、隐私挖掘）做安全盲测；
2. **训练数据脱敏**：从日志造数据前，清洗手机号、身份证、地址、订单号等 PII——模型会背训练数据，被诱导复述出来就是数据泄露事故；
3. **蒸馏数据的条款风险**：用 OpenAI 等闭源 API 生成训练数据去训练竞品模型，违反其服务条款。商用项目建议用开源许可宽松的强模型（如 DeepSeek、Qwen 系大杯）做数据生成；
4. **基座许可证复查**：Llama 系有月活与命名条款，商用前法务过一遍；Apache 2.0 系（Qwen 大部分版本）最省心；
5. **输出免责与人工兜底**：医疗、法律、金融等高危领域，模型输出必须有"仅供参考"声明和人工复核流程——这不是技术问题，是上线门槛。
