# 浙江移动垂类模型训练落地实施方案

> 针对四个立项问题的逐条解答 + 可执行路线图。硬件结论基于昇腾官方文档的实测锚点推算（公式全部给出，假设可替换）；方法结论标注论文/官方文档出处。配套阅读：同目录《大模型微调技术选型指南》《大模型训练阶段选择与数据集落地手册》。

**先报本方案依赖的两个已核实硬件事实：**

- 昇腾 910C：单卡 **128GB HBM**、约 800 TFLOPS FP16（双芯合封，约等于 2× 910B）；
- "8P64卡"按昇腾标准整机理解：**8 台 Atlas 服务器 × 每台 8 卡 = 64 张 910C，集群总显存 64 × 128GB = 8192GB（8TB）**。

---

## 问题一：基模选型有通用的方法论或原则吗？

**直接回答：有，四步漏斗法——硬约束筛选 → 公开能力初筛 → 自建盲测 → 小样本微调探针。每步都可执行、可量化。**

### 第一步：硬约束筛选（一票否决项，1 天完成）

| 约束 | 检查方法 | 对本项目的具体含义 |
|---|---|---|
| **昇腾适配** | 查 MindSpeed-LLM / MindIE 官方支持列表 | 不在列表里的模型，适配成本可能超过训练本身。Qwen2/2.5/3 全系、DeepSeek 系、Llama 系均在昇腾官方支持列表内 |
| 许可证 | 读 LICENSE | Qwen 主要版本 Apache 2.0 最省心；Llama 有自有条款需法务过 |
| 规模可部署 | 用推理预算倒推（见《落地手册》第六章） | 上线时单场景给多少卡、要求什么延迟，决定 7B/14B/32B/72B |
| 上下文长度 | 业务最长输入（工单+RAG 检索内容）实测 | 诊断分析场景拼上日志和知识库片段，建议 ≥32k 原生窗口 |
| 中文与领域底子 | 模型卡说明的训练语料构成 | 中文业务选中文语料占比高的家族（Qwen、GLM、DeepSeek、TeleChat） |

### 第二步：公开能力初筛（榜单只做粗筛，不做决策）

看 C-Eval / CMMLU / IFEval（指令遵循）划定 2~4 个候选。**榜单分数只用于淘汰明显弱的，不用于排序**——榜单污染是公认问题，排序必须靠下两步。

### 第三步：自建盲测集 zero-shot 摸底（3~5 天）

用问题四的方法先建 100~200 题的业务盲测集，候选模型不做任何训练直接答题、人工盲评。**这一步测的是"基座离业务的先天距离"**——先天近的基座，后续微调事半功倍。

### 第四步：小样本微调探针（每个候选 1~2 天）

各取同样的 1000 条业务 SFT 数据，统一 LoRA 配置（r=16、all-linear、lr 1e-4）快速训一轮，再盲测。**这一步测"可塑性"**：有的基座 zero-shot 一般但一训就起来，有的反之。两步得分加权（建议 4:6，微调后表现权重高）确定终选。

### 对本项目的具体建议

- **主力候选：Qwen2.5/Qwen3 系列**——昇腾适配最全（MindSpeed-LLM 官方提供从 7B 到 72B 的完整训练脚本与并行配置）、Apache 2.0、中文强、社区量化/部署生态最成熟；
- **对照候选：TeleChat2 系列**——中国电信 TeleAI 出品，**电信运营商同行先例，且整个系列完全在国产昇腾算力上训练**（115B 用 8000 张 NPU + MindSpore 4D 并行，技术报告 arXiv:2507.18013），电信领域语料占比天然高，与浙江移动的业务分布近；
- **诊断分析场景的补充候选：DeepSeek-R1 蒸馏系列**（推理增强，见问题三）。

## 问题二：64 张 910C，全量 SFT / LoRA / 部分参数训练的模型参数上限分别是多少？

**直接回答（8k 序列、bf16、AdamW 前提下）：**

| 训练方式 | 理论静态上限 | **工程可用上限（建议对外口径）** | 舒适区（生产建议） |
|---|---|---|---|
| 全量 SFT | ~380B | **约 130B~150B 稠密模型** | **≤72B** |
| 部分参数（解冻 1/4 层） | — | **约 180B~220B（仅比全量提升 1.3~1.5 倍）** | ≤110B |
| LoRA | ~2000B | **稠密 400B 级全覆盖；671B 级 MoE（如 DeepSeek-V3）可放下但工程复杂** | ≤72B 稠密随便训 |

### 计算过程（假设可替换，公式留给你复算）

**锚点（昇腾官方实测，不是推算）**：MindSpeed-LLM 官方文档给出 Qwen-72B 预训练、8k 序列、开重计算的配置需要 **64 × 910B（64GB）= 4096GB 总显存**。折算综合显存预算 ≈ 4096GB ÷ 72B ≈ **57 字节/参数**（这个数已包含权重 2 + 梯度 2 + 优化器 12（ZeRO 论文的 16 字节账）+ 激活 + 并行切分冗余 + 碎片，是"能以合理吞吐真跑起来"的真实预算，比纸面静态值 18 字节悲观得多，但可信）。

**全量 SFT 上限** = 8192GB ÷ 57 字节/参数 ≈ **144B**。即：64 张 910C 总显存正好是官方 72B 基准（64×910B）的两倍，参数上限也约为两倍。结论：
- **TeleChat2-115B 这个量级是本集群全量 SFT 的实际天花板**（放得下，吞吐偏低，适合一次性 SFT，不适合大数据量 CPT）；
- 72B 全量 SFT 很从容（相当于官方基准下显存余量翻倍，可以把重计算关掉换速度，或把序列拉长）；
- 想冲 200B：把序列降到 4k + 全量重计算 + 分布式优化器理论可达，但吞吐会差到没有实用价值，不建议作为口径。

**部分参数训练提升多少**：冻结部分只省"梯度+优化器状态"（14 字节/参数），**激活显存一点不省**（反向传播仍要穿过冻结层，见《选型指南》1.2）。解冻比例 f 的静态预算 = 2 + 16f 字节/参数：f=1/4 时从 18 降到 6，但占大头的激活和并行冗余不变，综合预算从 57 降到约 45 字节/参数 → 上限 8192÷45 ≈ **180B**；f=1/8 可到约 220B。**所以要给宁博一个明确的管理预期：部分参数训练只把上限提高 1.3~1.5 倍，它不是跳量级的手段；想跳量级，答案是 LoRA。**

**LoRA 上限**：冻结基座只需 bf16 权重 2 字节/参数 + 极小的 adapter 优化器状态，综合预算（含激活、TP/PP 冗余）约 3.5~4 字节/参数 → 上限 8192÷4 ≈ **2000B**。实际约束变成"开源模型本身多大"：Llama-3.1-405B（权重 810GB）轻松放下；DeepSeek-V3/R1 671B MoE（bf16 权重约 1.34TB）也在 8TB 总显存内，需 EP/PP 组合切分，工程复杂但可行。**一句话：本集群上 LoRA 没有实际参数上限，所有主流开源模型都能训。**

### 给领导汇报的一页结论

```
64 × 910C（8TB 总显存）：
├─ 全量 SFT：上限 ~140B（115B 级是天花板）；生产舒适区 72B
├─ 部分参数：上限 ~200B，只比全量多 1.3~1.5 倍，不解决量级问题
├─ LoRA   ：无实际上限（405B 稠密 / 671B MoE 均可），72B LoRA 非常宽裕
└─ 推荐主配方：72B 基座 —— 大数据 SFT 用全量，场景化迭代用 LoRA
```

### 三条 910C 工程注意

1. 训练框架优先 **MindSpeed-LLM**（昇腾官方 Megatron 路线，72B 级并行配置有现成脚本：TP8 + PP 组合 + 重计算）；轻量 LoRA 实验可用 LLaMA-Factory 的 torch-npu 后端，两者数据格式通用；
2. 并行配置纪律（华为云官方文档）：TP×PP×CP 必须整除总卡数，TP×CP 必须整除 num_attention_heads，GBS/MBS 必须被 DP 数整除——并行配置错误是昇腾上"训不起来"的第一大原因；
3. 4-bit 量化训练（QLoRA/bitsandbytes）在昇腾生态的成熟度不如 CUDA，**本集群显存充裕，统一用 bf16 LoRA，不要引入 QLoRA 的适配风险**。

## 问题三：知识理解、意图识别、诊断分析、指令生成四个场景，要不要分别训模型？

**直接回答：不是"一个大一统"也不是"四个模型"，推荐"一个基座 + 统一多任务 SFT 起步，按需分裂场景 LoRA，意图识别单独小模型"的三层结构。**

### 先按两个工程维度拆解四个场景

| 场景 | 任务本质 | 延迟/QPS 要求 | 关键依赖 |
|---|---|---|---|
| 意图识别 | 分类（封闭集合） | **极高 QPS、毫秒级**（每通对话入口都要过） | 标注数据 |
| 知识理解 | 知识问答/阅读理解 | 中 | **知识时效性 → 必须 RAG**，权重里记知识不可行（Biderman et al. 2024 的结论，见《选型指南》6.2） |
| 诊断分析 | 多步推理（告警→根因） | 低 QPS、可接受秒级 | 推理能力 → 模型规模是硬天花板 |
| 指令生成 | 严格格式的结构化输出（工单指令/网络配置） | 中 | 格式正确率**可自动验证** → 天然适合 GRPO/RLVR（《选型指南》7.4） |

### 推荐架构（三层）

```
第1层 意图识别：独立小模型（1.5B~7B 全参或 LoRA 微调）
        理由：分类任务小模型微调即可打平大模型（《选型指南》2.2），
             推理成本低一个数量级，入口高 QPS 扛得住
第2层 主力模型：72B 基座 + 统一多任务 SFT（知识理解/诊断分析/指令生成三场景数据混合训练）
        理由：FLAN（Wei et al. 2021）与 Scaling Instruction-Finetuned Models
             （Chung et al. 2022）的核心结论——多任务混合指令微调相互增益、
             提升跨任务泛化，任务间是互补不是干扰；知识理解场景配 RAG
第3层 场景 LoRA 分裂（按需，不预设）：当且仅当出现以下信号才把某场景拆出独立 adapter：
        ① 跷跷板效应：A 场景数据增多导致 B 场景盲测分明显下降
        ② 迭代节奏冲突：某场景每周要更新，其他场景一季度一更
        ③ 行为冲突：指令生成要绝对死板，诊断分析要发散推理，同权重难两全
        拆分后用同一基座挂多 LoRA 部署（S-LoRA，Sheng et al. 2023：
        单卡可同时服务上千个 adapter），推理侧成本几乎不增加
```

### 两个补充决策

- **诊断分析如果效果不达标**：升级路线是换推理增强基座（DeepSeek-R1 蒸馏版或 Qwen3 thinking 系）+ 把人工诊断报告整理成带思维链的 SFT 数据；若根因判断有标准答案（历史工单已知根因），可上 RLVR（判分函数=根因是否命中），这是不需要偏好标注的强化路线（DeepSeek-R1, 2025）。算法选择：稠密基座用 GRPO，MoE 基座用 GSPO（Qwen 团队 2025 结论：GRPO 长训在 MoE 上会崩，GSPO 原生稳定，Qwen3 即用 GSPO）；训练框架用 EasyR1（LLaMA-Factory 官方指向的 RLVR 姊妹项目）或 TRL/veRL；
- **指令生成的验收红线**：格式正确率（语法校验器自动判）必须 ≥99% 才能进入下一阶段评估，这一指标天然可做 GRPO 的奖励函数。

### 数据配比提醒

统一多任务 SFT 时按各场景上线流量比例配数据（而不是各场景数据量天然比例），并掺 1:1~1:5 的通用指令数据防遗忘（《落地手册》2.2）。某场景数据特别少（<1000 条）时，先并入多任务大锅训练蹭其他场景的泛化收益，不要单独训。

## 问题四：针对不同场景应用，评测集如何构建？有什么通用方法论？

**直接回答：有成熟方法论——"覆盖矩阵取材 + 分题型判分 + 三层评审 + 防污染 + 版本化回归"五步法。方法论框架来自 HELM（Liang et al. 2022，系统化多维评测）与 MT-Bench/LLM-as-Judge（Zheng et al. 2023，裁判偏置的实证研究）。**

### 第一步：按"覆盖矩阵"取材，不要随手攒题

每个场景建一张二维矩阵：**业务子类 × 难度档**，每个格子定配额，按格子填题。题目三个来源按优先级：①真实工单/对话日志脱敏抽样（占 60%+）；②业务专家出题覆盖边角与高危案例（25%）；③对抗题——模糊表述、多意图混合、超范围问题、诱导性问题（15%）。

| 场景 | 子类示例 | 规模下限 | 关键设计 |
|---|---|---|---|
| 意图识别 | 按意图类别全覆盖 | **每类 ≥50 题**，含易混淆类别对抗对 | 必须含"无法识别/超范围"类 |
| 知识理解 | 按知识域（资费/网络/业务规则…） | 200~500 题 | 答案标注出处文档，区分"模型该答"与"该查 RAG" |
| 诊断分析 | 按故障类型 × 根因层级 | 100~200 案例 | 用历史已结案工单，根因是客观标准答案 |
| 指令生成 | 按指令模板类型 | 100~200 题 | 每题附 schema/语法校验器 |

### 第二步：分题型设计判分方式（能自动判的绝不人工）

| 题型 | 判分方式 | 指标 |
|---|---|---|
| 分类（意图识别） | 全自动 | Macro-F1（类别不平衡时不要用 Accuracy）、混淆矩阵 |
| 抽取/有标准答案（诊断根因） | 全自动 | EM / 命中率 |
| 结构化输出（指令生成） | 全自动（schema 校验 + 字段比对） | 格式合法率、字段准确率 |
| 开放生成（知识理解的解释类） | Rubric 评分表 + LLM 裁判预筛 + 人工抽检 | 1~5 分制：正确性/完整性/简洁性/合规性四维分别打分 |

### 第三步：开放题的三层评审（控制成本又保住可信度）

1. **LLM-as-Judge 批量预筛**，必须做三个偏置防控（Zheng et al. 2023 实证发现的三大裁判偏置）：位置偏置→每对回答正反序各评一次，不一致记平手；长度偏置→评分提示中明确"简洁完整优于冗长"；自恋偏置→裁判模型不得与被评模型同家族；
2. **人工盲评**抽 20%~30% 校准裁判（裁判与人工的一致率 <80% 时裁判结果作废）；
3. **上线决策只认人工盲评 + 业务指标**，LLM 裁判只用于版本间快速筛选。

### 第四步：防污染（评测可信度的生命线）

- 评测集**物理隔离**于训练数据管线，建数据集时先做训练集与评测集的 n-gram 去重比对；
- 评测题每季度轮换 20%~30%（旧题可能随日志数据间接漏入训练集）；
- 公开榜单（C-Eval/CMMLU）只用于通用能力回归监控，**不作为业务验收依据**——污染风险且与业务无关。

### 第五步：版本化与回归闭环

- 评测集与模型同等管理：版本号、变更记录、新旧版本平行跑一期再切换；
- **坏案例回流**：每个线上事故/坏案例修复后加入评测集，防同一问题在后续版本复发；
- 通用能力回归固定三件套：CMMLU 抽样 + 20 条日常闲聊盲测 + 安全红线题（防灾难性遗忘与安全退化，《落地手册》第七/十章）。

### 领域现成资源

电信领域已有公开基准 **TeleQnA**（Bornea et al. 2023，arXiv:2310.15051，10,000 道电信知识问答，源自标准文档与研究文献），可直接作为"电信领域通识"维度的回归集，省一部分自建工作量；业务私有场景仍需按上述五步法自建。

## 落地路线图（按依赖关系排序，非日历排期）

```
阶段 0（先于一切）：四个场景的评测集建设（问题四的五步法）+ 训练数据盘点脱敏
        ——评测集不就绪，后面所有实验都无法判断好坏

阶段 1：基模选型漏斗（问题一的四步法）
        产出：主力基座定版（预期 Qwen 系 72B 级）+ 意图识别小基座定版

阶段 2：意图识别小模型先行（数据最规整、判分全自动、见效最快）
        ——用最容易的场景打通"训练→评测→部署"全链路，暴露昇腾工程问题

阶段 3：主力模型统一多任务 SFT（72B LoRA 起步，数据配比按流量；
        效果到顶且数据量 >10 万再评估升级全量 SFT，本集群 72B 全量很从容）
        + 知识理解场景同步建 RAG 管线

阶段 4：按盲测结果决定是否分裂场景 LoRA（问题三的三个分裂信号）
        诊断分析不达标 → 换推理基座/上 GRPO；指令生成格式率不达标 → GRPO

阶段 5：上线灰度 + 数据飞轮（《落地手册》第九章：点赞点踩→KTO/DPO 迭代，
        每 2~4 周从基座全量数据重训，盲测胜出再放量）
```
