# 大模型微调技术选型指南

> 覆盖全参数训练、部分参数训练（Freeze）、LoRA、QLoRA 四种微调方式的技术原理、选型框架、数据量要求与资源约束。所有数字均来自工程实践中的典型量级，可直接用于立项评估和资源申请。

---

## 一、四种微调方式的技术本质

### 1.1 一句话定义

| 方法 | 一句话本质 | 可训练参数占比 | 基座权重精度 |
|---|---|---|---|
| 全参数训练（Full FT） | 解冻所有权重，整个模型重新学 | 100% | bf16/fp16 |
| 部分参数训练（Freeze/Partial） | 只解冻部分层，其余冻结 | 5%~30%（取决于解冻多少层） | bf16/fp16 |
| LoRA | 冻结全部原权重，旁路挂一对低秩矩阵学"增量" | 0.1%~1% | bf16/fp16 |
| QLoRA | LoRA 的省显存版：基座压成 4-bit，只有旁路是高精度 | 0.1%~1% | 4-bit（NF4） |

### 1.2 核心实现原理

#### （1）全参数训练

反向传播更新模型每一个权重。难点不在算法，在显存账：用 AdamW 优化器训练时，每个参数要存——

- 权重本身（bf16，2 字节）
- 梯度（bf16，2 字节）
- 优化器一阶动量 m（fp32，4 字节）
- 优化器二阶动量 v（fp32，4 字节）
- fp32 主权重副本（混合精度训练需要，4 字节）

合计 **约 16 字节/参数**，再加上激活值（与 batch size、序列长度成正比）。一个 7B 模型仅静态开销就约 112GB，**这就是为什么全参数微调 7B 至少要 4~8 张 80G 卡（配合 ZeRO/FSDP 切分）**，单卡根本放不下。

它的回报是：所有权重都可以动，能改变模型的"深层行为"——注入新知识、学新语言、做领域继续预训练，这些是其他方法很难替代的。

#### （2）部分参数训练（Freeze）

把大部分层 `requires_grad=False`，只训练若干层。常见三种解冻策略：

- **解冻最后 N 层 Transformer block**（最常用，对应 LLaMA-Factory 的 `freeze_trainable_layers`）：模型高层负责任务相关的抽象表示，改高层对输出行为影响最直接；
- **只解冻 embedding + lm_head**：适合扩词表、适配新语言的第一阶段；
- **只解冻 bias（BitFit 思路）**：极端省资源，现在基本被 LoRA 取代。

显存节约来自：冻结层不存梯度和优化器状态。但要注意一个常被忽略的事实：**只要可训练层不在最底层，前向激活仍要全量保存**（反向传播要穿过冻结层把梯度传到可训练层），所以激活显存省不了多少，节约幅度不如直觉中大。

#### （3）LoRA（Low-Rank Adaptation）

理论出发点：**微调引起的权重变化量 ΔW 是低秩的**——模型适配一个新任务，实际只需要在一个很小的子空间里调整。于是不直接改 W，而是旁路学一个低秩分解：

```
W' = W + (alpha/r) · B·A
其中 W ∈ R^(d×k) 冻结不动；B ∈ R^(d×r)，A ∈ R^(r×k)，r 通常取 8~128，远小于 d、k
```

以 7B 模型、r=16、挂全部线性层为例，可训练参数约 4000 万，**只占 0.6%**。梯度和优化器状态只需要为这 0.6% 维护，显存从 112GB 量级直接降到 20GB 以内。

工程上的两个关键收益：

- **训练完可以把 BA 合并（merge）回 W**，推理零额外延迟，部署和原模型完全一样；
- **不合并则可以热插拔**：一个基座 + N 个几十 MB 的 adapter，服务 N 个业务，多租户场景成本极低。

关键超参（实践默认值）：

| 超参 | 推荐值 | 说明 |
|---|---|---|
| r（秩） | 8~64 | 数据少/任务简单用 8~16；数据多/任务难用 32~64。r 翻倍≠效果翻倍，先调数据再调 r |
| lora_alpha | 2×r | 缩放系数，固定 alpha/r=2 即可，不必单独调 |
| target_modules | **all-linear**（q,k,v,o,gate,up,down 全挂） | 早期论文只挂 q,v 是为了省事，实测全挂明显更好，这是新项目的默认正解 |
| 学习率 | 1e-4 ~ 3e-4 | **比全参数高约一个数量级**（全参数通常 1e-5~2e-5）。照搬全参数学习率是 LoRA 不收敛最常见的原因 |
| lora_dropout | 0.05~0.1 | 数据少时开，数据多可设 0 |

#### （4）QLoRA

QLoRA = **4-bit 量化基座 + LoRA**，三项核心技术：

1. **NF4 量化**（4-bit NormalFloat）：针对权重服从正态分布的特点设计的 4-bit 数据类型，比普通 int4 信息损失小；
2. **双重量化**：把量化常数本身再量化一次，每参数再省约 0.4 bit；
3. **Paged Optimizer**：显存峰值时把优化器状态换页到 CPU 内存，防 OOM。

基座以 4-bit 存储（约 0.5 字节/参数），前向/反向计算时逐块反量化为 bf16 参与运算，LoRA 旁路始终保持 bf16 精度并接收全部梯度更新。

代价两条，立项时必须知道：

- **训练速度比 LoRA 慢 30%~50%**（反量化开销）；
- **有量化误差**。论文结论是"与 16-bit 全参微调可比"，工程实测：对话/风格类任务确实几乎无损；数学、代码、复杂推理类任务比 bf16 LoRA 低 1~2 个点。**QLoRA 不是免费午餐，是"用时间和一点精度换显存"。**

### 1.3 四者的内在关联

四种方法在同一条光谱上，本质都是在回答一个问题：**给模型多少"自由度"去改变自己？**

```
全参数 ──────→ Freeze ──────→ LoRA ──────→ QLoRA
全部自由度      子集自由度      低秩子空间      低秩子空间 + 基座降精度

自由度递减 → 显存递减 → 需要的数据量递减 → 过拟合风险递减 → 能力改造上限递减
```

两条推论，是后面所有选型逻辑的根基：

1. **自由度和数据量必须匹配。** 可训练参数越多，需要越多数据去约束它，否则过拟合 + 灾难性遗忘。"数据少所以用全参数好好学"是方向完全反掉的错误直觉——数据少恰恰应该用 LoRA。
2. **任务对模型的"改造深度"决定方法下限。** 改说话风格、输出格式 → 低秩增量足够；注入新知识、学新语言 → 需要动 embedding 和大量权重，LoRA 的低秩瓶颈就不够用了。

## 二、多维度选型框架

### 2.1 按模型参数规模

| 模型规模 | 典型代表 | 首选 | 备选 | 实践要点 |
|---|---|---|---|---|
| 小（≤3B） | Qwen2.5-0.5B/1.5B/3B | **全参数** | LoRA | 小模型全参微调单卡 80G（甚至 4090 + ZeRO offload）就能跑，且小模型容量有限，LoRA 的低秩约束伤害相对更大，能全参就全参 |
| 中（7B~14B） | Qwen2.5-7B、Llama-3-8B | **LoRA** | 全参（有 8×A100 且任务需要）；QLoRA（只有消费卡） | 工业界最主流区间。90% 的业务需求 LoRA 就到位；只有知识注入/行为大改才上全参 |
| 大（30B~70B） | Qwen2.5-72B、Llama-3-70B | **LoRA（多卡）/ QLoRA（单卡 48G 或 2×24G）** | 全参（仅大规模集群） | 70B 全参微调静态显存超 1TB，需要数十张 A100 + ZeRO-3，不是一般团队的选项 |
| 超大（100B+ / MoE） | DeepSeek-V3 级别 | **QLoRA/LoRA**，或干脆不微调 | — | 这个量级先认真评估 RAG + 提示工程 + Few-shot 能不能解决，微调是最后手段 |

### 2.2 按任务类型

| 任务类型 | 推荐方法 | 理由与落地细节 |
|---|---|---|
| **分类 / 打分 / 奖励模型** | LoRA（r=8~16），数据极少时 Freeze（最后 2~4 层 + 分类头） | 输出空间小，不需要改造生成能力。注意：百条级数据时先试试不微调、直接 few-shot prompt |
| **风格 / 格式生成**（客服话术、固定 JSON 输出、文案口吻） | **LoRA，最典型的甜点场景** | 这类任务本质是"输出分布的低秩偏移"，与 LoRA 假设完全吻合。几千条数据、r=8~16、单卡几小时搞定 |
| **指令微调（通用 SFT）** | 数据 <10 万条 → LoRA（r=32~64, all-linear）；数十万条高质量数据且追求上限 → 全参数 | LLaMA-Factory 表中所有 SFT 路线四种方式都支持，瓶颈在你的数据量配不配得上自由度 |
| **领域知识注入**（医疗/法律/金融继续预训练） | **全参数 或 Freeze（高层 + embedding）**，LoRA 不推荐当主力 | "记住新知识"需要改写大量权重中的事实存储，低秩增量装不下。数据要求是 GB 级 token（见第三章）。预算不够时，正确答案是 **RAG，不是 LoRA 硬训** |
| **新语言 / 扩词表** | 必须动 embedding：全参数，或分阶段 Freeze（先只训 embedding+lm_head，再放开高层） | 任何不解冻 embedding 的方法对新 token 都无能为力 |
| **多模态微调**（LLaVA 类架构） | 分模块组合：**projector 全参 + LLM 用 LoRA + 视觉编码器冻结** | 多模态不是单选题，是按模块拆开各用各的。第一阶段对齐训练只训 projector；第二阶段指令微调时 LLM 挂 LoRA |
| **偏好对齐（DPO/KTO/ORPO/SimPO）** | **LoRA 优势特别明显** | DPO 需要策略模型 + 参考模型两份权重；LoRA 下参考模型 = 关掉 adapter 的同一基座，**直接省掉一份完整模型的显存**。这是 LoRA 在对齐训练中近乎默认的原因 |
| **PPO（RLHF）** | LoRA / QLoRA | PPO 同时挂 actor、critic、reward、reference 四个模型，全参数训练的显存是天文数字，没有 LoRA 基本玩不动 |

### 2.3 选型决策树（可直接执行）

```
Q1. 任务需要注入新知识 / 新语言 / 大幅改变模型底层能力吗？
 ├─ 是 → Q1a. 有 GB 级领域语料 + 多卡 A100 集群吗？
 │        ├─ 有 → 全参数（或 Freeze 分阶段），按继续预训练流程走
 │        └─ 没有 → 别硬训，上 RAG / 换更强基座
 └─ 否（风格、格式、指令遵循、对齐类） → Q2

Q2. 显存够把基座以 bf16 放下并留出激活空间吗？
     （经验线：模型参数量 GB 数 × 2 + 30% 余量 ≤ 单卡或合计显存）
 ├─ 够 → LoRA（默认 all-linear，r 按数据量定）
 └─ 不够 → QLoRA（接受慢 30~50% 和 1~2 个点的精度风险）

Q3.（仅当 Q2 选了 LoRA 且效果到顶仍不满足）
 数据量 ≥ 10万高质量样本，且有 8 卡级算力？
 ├─ 是 → 升级全参数，博最后 1~3 个点
 └─ 否 → 优化数据质量比换方法收益大，回去洗数据
```

## 三、数据量的量化要求

### 3.1 各方法 × 各任务的数据量阈值（指令格式样本数）

下表是工程实践中"能看到效果的下限"和"收益开始饱和的区间"，不是论文里的理想值：

| 场景 | 方法 | 最低起效量 | 舒适区间 | 饱和点 |
|---|---|---|---|---|
| 文本分类（每类） | LoRA/Freeze | 50~100 条/类 | 500~1000 条/类 | ~5000 条/类 |
| 风格/格式生成 | LoRA | 300~500 条 | 1k~5k 条 | ~1 万条 |
| 垂直领域问答（知识在 prompt/RAG 里，模型只学回答方式） | LoRA | 1k 条 | 5k~5 万条 | ~10 万条 |
| 通用指令微调 SFT | LoRA | 5k 条 | 2 万~10 万条 | 数十万条 |
| 通用指令微调 SFT | 全参数 | 1 万条（低于此过拟合风险高） | 5 万~50 万条 | 百万条级 |
| 领域知识注入（继续预训练） | 全参/Freeze | **100M token**（低于此基本无感） | 1B~10B token | 视领域而定 |
| DPO/ORPO/SimPO 偏好对 | LoRA | 2k~5k 对 | 1 万~5 万对 | ~10 万对 |
| 奖励模型 | LoRA | 5k 对 | 2 万~10 万对 | — |

两个必须记住的特例：

- **LIMA 现象**：1000 条极高质量、多样性极好的数据全参微调也能出好模型——但前提是"极高质量"，绝大多数团队自认为的高质量数据达不到，**不要拿 LIMA 当少数据上全参的理由**；
- **知识注入的 100M token 红线**：很多团队拿几万条领域 QA 做 LoRA 就期望模型"学会医疗知识"，实际只学会了"医疗腔"。知识注入是预训练级任务，几万条 QA 远远不够。

### 3.2 数据量—模型—方法的匹配关系（核心规律）

1. **数据量跟着"可训练参数量"走，不是跟着模型大小走。** 70B 模型挂 r=16 的 LoRA，可训练参数和 7B 挂 LoRA 是同一量级，所以需要的数据量也是同一量级。这是"大模型 + LoRA + 小数据"能成立的根本原因。
2. **基座越强，需要的数据越少。** 同一个任务，Qwen2.5-72B + 1k 条 LoRA 的效果，常常好于 7B + 1 万条。预算允许时，"换大基座 + 少数据 LoRA"通常优于"小基座 + 堆数据"。
3. **LoRA 的 r 与数据量挂钩**：几千条 → r=8~16；几万条 → r=32；十万条以上 → r=64 或考虑全参。数据少还开大 r，等于给了过拟合的自由度。
4. **Epoch 数与数据量反向**：<5k 条可以跑 3~5 epoch（盯紧验证集 loss，过拟合迹象立刻停）；>5 万条跑 1~2 epoch 足够；全参数几乎永远 ≤2 epoch。
5. **防遗忘配比**：做领域 SFT 时按 **领域数据 : 通用数据 ≈ 1:1 到 1:5** 掺入通用指令数据，否则模型学会了你的任务、忘掉了通用能力（全参数下尤其严重，LoRA 下也存在）。
6. **质量 > 数量，且是数量级意义上的大于**：去重、去模板化、答案正确性核验、长度和题型多样性，这四件事做好，3k 条顶得上没洗过的 3 万条。微调项目失败的第一原因永远是数据，不是方法选错。

## 四、资源消耗、速度与效果上限对比

### 4.1 训练显存需求（bf16、AdamW、batch=1、4k 上下文，含激活的工程估算）

| 模型 | 全参数 | Freeze（训 1/4 层） | LoRA | QLoRA |
|---|---|---|---|---|
| 7B | ~120GB（≥2×80G，推荐 4~8×A100） | ~55GB（1×80G） | **~18GB（1×24G，如 4090）** | **~8GB（1×12G）** |
| 14B | ~240GB（≥4×80G） | ~110GB（2×80G） | ~34GB（1×40G/48G） | ~12GB（1×16G） |
| 34B | ~600GB（8×80G+） | ~260GB（4×80G） | ~76GB（1×80G） | ~24GB（1×24G，贴边） |
| 70B | ~1.2TB（16~32×80G + ZeRO-3） | ~520GB（8×80G） | ~155GB（2×80G） | **~42GB（1×48G 或 2×24G）** |

> 速算公式：全参数 ≈ 参数量(B)×16~18 GB；LoRA ≈ 参数量(B)×2 GB + 2~6GB 激活；QLoRA ≈ 参数量(B)×0.55 GB + 2~6GB 激活。开 gradient checkpointing（默认都该开）后激活项可控；序列拉到 32k 以上时激活会反超权重项，需另行估算。

### 4.2 速度与收敛

| 维度 | 全参数 | Freeze | LoRA | QLoRA |
|---|---|---|---|---|
| 单步耗时（同卡数） | 基准 | 略快于全参 | 与全参接近（前向不省，省的是优化器更新和通信量） | **慢 30%~50%**（反量化开销） |
| 收敛所需 epoch | 最少（1~2） | 少 | 略多（用 1e-4 级学习率补偿后差距很小） | 同 LoRA |
| 多卡扩展性 | 需要 ZeRO/FSDP，通信重 | 中等 | 极好（梯度同步量只有 adapter 大小） | 极好 |
| 总训练成本（同任务同效果） | 最高（卡数 × 时间） | 中 | **最低** | 卡时单价低但时长 +30~50%，总成本通常仍低于 LoRA 多卡方案 |

### 4.3 效果上限

```
全参数 ≥ Freeze ≈ LoRA(all-linear, r 足够) > QLoRA
```

按任务拆开看（差距为典型 benchmark 分差）：

| 任务类型 | LoRA vs 全参 | QLoRA vs LoRA |
|---|---|---|
| 风格/格式/对话 | **基本无差距（<0.5 点）** | 基本无差距 |
| 通用指令遵循 | 0~1 点 | 0~1 点 |
| 数学/代码/复杂推理 | 全参领先 1~3 点 | LoRA 领先 1~2 点 |
| 知识注入/继续预训练 | **全参显著领先，LoRA 不胜任** | — |

结论：**任务越"浅"（改输出分布），方法之间越无差别；任务越"深"（改内部知识与推理），自由度高的方法优势越大。** 用差距大小反推：如果你的 LoRA 和全参在你的任务上跑出 5 个点以上的差距，先怀疑 LoRA 配置错了（学习率照搬全参、只挂了 q,v、r 太小），而不是急着下"LoRA 不行"的结论。

### 4.4 一页式速查表

| | 全参数 | Freeze | LoRA | QLoRA |
|---|---|---|---|---|
| 7B 最低硬件 | 2~8×A100-80G | 1×A100-80G | 1×4090-24G | 1×3060-12G |
| 70B 最低硬件 | 数十卡集群 | 8×A100 | 2×A100-80G | 1×48G / 2×24G |
| 最低有效数据量 | ~1 万条 | ~5k 条 | **~500 条** | ~500 条 |
| 学习率量级 | 1e-5~2e-5 | 1e-5~5e-5 | **1e-4~3e-4** | 1e-4~3e-4 |
| 效果上限 | ★★★★★ | ★★★★ | ★★★★ | ★★★☆ |
| 灾难性遗忘风险 | 高 | 中 | **低** | 低 |
| 部署复杂度 | 直接替换权重 | 直接替换 | merge 后零开销 / 不 merge 可热插拔 | 同 LoRA（merge 时注意要合到 bf16 基座上再量化，勿在 4-bit 上直接合） |
| 知识注入能力 | ★★★★★ | ★★★ | ★ | ★ |
| 典型适用 | 继续预训练、大改行为、新语言 | 扩词表过渡阶段、折中方案 | **90% 的业务微调需求** | 显存受限下的 LoRA 平替 |

## 五、常见误区（每条都来自真实踩坑）

1. **"数据少，所以用全参数好好学"** —— 反了。数据少更要用 LoRA 收紧自由度；几百条数据全参微调 = 过拟合 + 灾难性遗忘双杀。
2. **"用 LoRA 给模型灌领域知识"** —— 低秩增量装不下知识。几万条领域 QA 的 LoRA 只会让模型学会领域口吻。知识问题用 RAG 或继续预训练解决。
3. **LoRA 学习率照搬全参数的 2e-5** —— loss 几乎不降，然后得出"LoRA 没用"的错误结论。LoRA 学习率要高一个数量级。
4. **target_modules 只挂 q,v** —— 这是 2021 年论文的省事配置，今天的正确默认是 all-linear，效果差距明显。
5. **把 QLoRA 当免费午餐** —— 它慢 30~50%，复杂任务掉 1~2 个点。显存够放 bf16 基座时，直接用 LoRA。
6. **不掺通用数据做 SFT** —— 模型学会你的任务、忘了说人话。领域:通用 ≈ 1:1~1:5 掺着训。
7. **效果不好先换方法** —— 微调效果的影响排序是：**数据质量 > 基座选择 > 数据量 > 超参 > 微调方法**。方法选型只决定"能不能跑得起、上限在哪"，决定下限的永远是数据。
8. **跳过"要不要微调"这一问** —— prompt 工程 + few-shot + RAG 能解决的，不要微调。微调引入训练、评估、部署、迭代的全套维护成本，它应该是手段穷尽后的选择，不是起手式。

## 附：与图中训练阶段矩阵的对应关系

图中（LLaMA-Factory）预训练、SFT、奖励模型、PPO、DPO、KTO、ORPO、SimPO 八个阶段均支持四种参数策略，因为**"训练阶段"和"参数更新策略"是两个正交的维度**——前者决定 loss 怎么算，后者决定哪些参数参与更新。工程上的高频组合：

- 预训练/继续预训练 → 全参数（知识注入需要全自由度）
- SFT → LoRA（业务主力），大厂大数据场景全参数
- 奖励模型 → LoRA（判别任务，低秩足够）
- PPO → LoRA/QLoRA（四模型并存，显存压力决定一切）
- DPO/KTO/ORPO/SimPO → LoRA（参考模型可与基座共享权重，省一份模型显存）
